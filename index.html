01 — TRADING JOURNAL

A futures journal that survives
changing the instrument.

A desktop journal for futures trading: log the trade, read the month back, find out which setup actually pays for itself. Six analytic views over one database, and a year of history that stays correct when the instrument underneath it changes.

The decision: store distance, not money

A trade is saved as a distance in ticks plus the instrument it was taken on. Dollars, R-multiples and every statistic are derived at read time from that instrument's tick value and commission.

What it gave: change the contract or the position size and the whole history recalculates itself. A spreadsheet keeps showing the old figures and never mentions it.

The decision: one file, nothing installed

The interface is HTML drawn by WebView2, which Windows already has. The logic underneath is the Python standard library and SQLite — no framework, no third-party package.

What it gave: the journal ships as a single 13.6 MB executable. It opens on a machine with nothing prepared, and there is no dependency to repair a year later.

The decision: never wait for silence

Audio is cut into phrases as it arrives instead of waiting for silence, and a finished piece enters recognition while the next one is still being spoken. The generated voice begins on the part that is already translated.

What it gave: 275–520 ms measured from the end of a phrase to the first translated sound, because only the tail is still in flight. A system that waits for the full utterance pays for all of it.

The decision: a second pass over the translation

Raw machine translation was right about 70% of the time on my test material. A quality layer sits behind it: a glossary of terms that must not drift, corrections for the constructions the model reliably breaks, and a check that what came out is a usable sentence at all.

What it gave: 97% on a held-out set the rules were never written against — the figure worth quoting, rather than the higher one from the material they were tuned on.

03 — LIVE FACE MASK

Five neural networks per frame,
inside 33 milliseconds.

It replaces the face in a live webcam feed while the camera is running and hands the finished picture to OBS as an ordinary window — no plugin, no virtual camera driver, nothing installed into OBS. Detection, 106 landmarks, identity embedding, generation and face parsing happen on every frame that passes through.

Working · ~100 ms camera to stream
  • Written in C++17 with GPU inference — not a Python wrapper
  • Per-stage latency shown live, so a slow frame has a name
  • Every output frame carries a permanent AI label that cannot be switched off

The decision: C++, and the frame never leaves the GPU

Thirty frames a second leaves 33 ms for all five networks, which ruled out Python early. The app is C++17 with ONNX Runtime on CUDA, and a frame stays in video memory from capture through to compositing — no copy back to the CPU between stages. Each stage reports its own milliseconds on screen.

What it gave: about 100 ms from camera to stream, and a slow frame has a name rather than a shrug.

The decision: cut along the face, not along an ellipse

The generated face is blended through the parsing map computed for that same frame, so hair, glasses and a hand crossing the cheek stay where they are. The original mouth and eyes can be kept untouched.

What it gave: lip-sync stays exact, because the mouth on screen is the real one — the detail that gives a swap away before anything else does.

The label is burned into the picture

“AI-generated face effect” goes on last, over everything, with no switch to remove it. Platforms strip metadata, so a line written into the pixels is the only kind that survives re-encoding, download and re-upload.

04 — AI TELEGRAM BOT

One chat window,
eighteen models behind it.

Send a photo, a voice message, a spreadsheet or a bare link, and whichever model suits that question answers it — including when the subject changes mid-conversation and then changes back. There is no mode to choose and no command to learn.

Live on Telegram
  • Produces real .pptx decks and .docx papers in 11 regional standards
  • Builds trading indicators for 7 platforms, compiling .jar studies server-side
  • Voice messages reach the model as audio, with no transcription step in between

The decision: the router picks the model, not the person

Every message is read for intent first — what kind of task it is, whether it needs vision, a long context or code — and that decides both the subject and the order of models to try. Ratings left on answers change which model wins next time.

What it gave: nobody has to know which of eighteen models is good at what, and the nineteenth can be added without a single user changing a habit.

The decision: official APIs, and the shortcut refused

Consumer AI subscriptions can be resold by driving them through captured browser sessions, and that is how a lot of these bots are built. This one runs on the providers' paid APIs.

What it gave: a service that still works the week a provider tightens enforcement, instead of one that disappears along with the account it was riding on.

The decision: four layers, so a change lands in one

Telegram, business logic, providers and storage are separate, with the boundaries held to. A new model is a change in the provider layer; a new interface language is a change in presentation; the tariff arithmetic lives in one place with a test suite of its own.

What it gave: eighteen providers and three languages accumulated over time without the code turning into a knot.

A missing key hides the feature

The bot starts with a single provider key — the free Gemini one is enough. Any platform without a key does not appear in the menu at all, rather than appearing and failing when pressed. Nothing in the interface looks alive and does nothing.

How I work

Nothing in common technically.
One way of working.

A desktop application, a real-time GPU pipeline, local speech AI and a service over eighteen model providers share no code and barely any vocabulary. What they do share is how each one got decided, built and checked — and that is the part that transfers to whatever a company happens to be building.

It starts as a specification

What the thing must do, who is holding it, and what would make it useless — written down before any architecture exists. The arguments that otherwise arrive in week six happen on page one, when changing your mind is free.

The architecture answers one constraint

Each product has a single constraint that decides its shape: 33 ms per frame, a trader who will not install a runtime, a streamer with no spare monitor for the output window. I find the one that actually binds and build outward from it.

Numbers come from measurement

Latency is broken down by stage and displayed while the thing runs; accuracy is read off material the rules never saw. Any figure I cannot reproduce on demand does not go on this page or into a conversation.

Failure is named, not hidden

A feature that cannot work is shown disabled with the reason beside it. When a camera hands over the wrong pixel format the application says so, rather than leaving someone with a bad frame rate and a guess.

The implementation is written with an AI coding tool

I set the requirements, decide how the product behaves, make the architecture calls and test every build against real use; the code is written alongside an AI assistant. That is the reason one person covers four technical areas in eighteen months, and it is the same leverage I would bring to a team.
